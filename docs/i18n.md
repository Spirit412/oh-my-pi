# Localization (i18n)

Status: all planned phases complete. Operator-facing UI, built-in text, CLI
help, settings, and installed-plugin catalogs are localized, with coverage
and pseudo-locale checks enforcing the result. This document remains the
working reference for keys, precedence, and test strategy.

## Goals

- One English source text, with Russian translations shipped in-tree.
- A late-bound translator usable from both `@oh-my-pi/pi-utils` consumers
  (`@oh-my-pi/pi-tui`, `@oh-my-pi/pi-coding-agent`) without changing every
  component signature.
- A public registration surface so extensions and installed plugins can ship
  their own catalogs.
- Deterministic English output in tests and headless protocol modes.

## Non-goals

- Model-facing text: system prompts, tool schemas/descriptions, judge prompts,
  and the text sent to providers stay English.
- Settings parameter names and submenu option labels: shipped as English values
  in every catalog so the settings panel matches config keys and documentation;
  setting and option descriptions localize.
- Identifiers and protocol values: command names, flag names, setting ids,
  model/provider ids, tool names, ACP/RPC method ids, persisted sentinels
  (`USER_INTERRUPT_LABEL`, `GENERIC_ABORT_SENTINEL`), and strings compared by
  code rather than displayed.
- Translating user content, session transcripts, or third-party output.

## Architecture

### Engine

`@oh-my-pi/pi-utils/i18n` owns:

- locale normalization (`ru-RU`, `ru_RU.UTF-8` → `ru`),
- ambient locale state (`setLocale` / `getLocale`),
- catalog registration and lookup,
- `t(key, fallback, params)` with `{placeholder}` interpolation,
- plural selection through `Intl.PluralRules`.

The English source text is the inline fallback:

```ts
t("omp.approval.allow", "Allow tool: {name}", { name })
```

This keeps English behavior byte-identical when no catalog is registered and
avoids a mandatory English catalog import. A generated `en.json` is still
useful for translators and coverage checks.

### Keys

- Core: `omp.<area>.<surface>.<name>` (for example `omp.approval.deny`).
- TUI: `tui.<area>.<surface>.<name>` (for example `tui.modelPicker.title`).
- Plugin: `plugin.<package-name>.<key>`; the loader adds the prefix so plugin
  catalogs cannot silently shadow core keys.
- Keys are stable. Renaming a key is a translation-breaking change and must
  update every shipped catalog.

### Locale resolution

Precedence, highest first:

1. `--lang <tag>`
2. `OMP_LANG` (declared as the `language` setting's env override)
3. `language` setting (`auto`, `en`, `ru`, or a BCP-47 tag)
4. `LC_ALL` / `LC_MESSAGES` / `LANG` when the setting is `auto`
5. `en`

`C`/`POSIX` resolve to English. Unknown locales keep their tag but fall back to
English messages until a catalog exists. Under `bun test`, `auto` resolves to
English unless `--lang` or `OMP_LANG` is explicit, so host locale cannot break
English assertions.

### Catalogs and precedence

- Core/package catalogs register at import time.
- Extension catalogs register through `pi.i18n.registerCatalog(...)`.
- Plugin catalogs load from the installed package before UI startup.
- Later registrations win within a namespace; disposing a registration restores
  the previous one. Missing keys fall back to the inline English default.

### Late binding

Strings evaluated at module import cannot react to a locale change. Any
translatable module-level literal must become either a getter or a `t()` call at
render time. Existing `get description()` getters and settings getters are the
pattern to follow.

### Formatting

Dates, numbers, and plurals go through the current locale. Table/chart alignment
keeps an explicit `pinned: "en-US"` mode so column widths remain deterministic.
Russian plural categories are `one`, `few`, `many`, and `other`.

### Plugins

Plugin manifest (`package.json#omp`):

```json
{
  "locales": {
    "ru": "./locales/ru.json"
  }
}
```

The loader resolves paths inside the plugin root, validates the catalog, prefixes
keys with `plugin.<package-name>.`, and registers it for startup. Extension
modules use the runtime API:

```ts
pi.i18n.registerCatalog("ru", catalog);
pi.i18n.t("plugin.example.greeting", "Hello");
```

## Test strategy

- Default locale in tests is English (`resolveLocale` forces it under
  `isBunTestRuntime` unless `OMP_LANG`/`--lang` is explicit).
- `resetI18nForTest()` in `afterEach` for tests that register catalogs or change
  locale; do not let ambient state leak between files.
- Unit tests: normalization, interpolation, plural categories, registration
  precedence, disposal, missing-key fallback.
- Contract tests: English output unchanged for approvals/help; Russian output
  for the same flows with `OMP_LANG=ru`.
- Width tests: run key TUI surfaces with `ru` and assert no critical action is
  truncated.
- Negative tests must not rely on English absence; assert keys or semantic
  markers instead.
- Pseudo-locale: run a surface with `--lang en-XA` (or `setLocale("en-XA")` in
  tests) to expose English fallbacks as accented, ~30% longer bracketed text;
  any accented label is an untranslated key, and the padding stresses widths.
- Coverage: `bun run check:i18n` fails when a runtime or literal `t()` key has
  no Russian entry, or a shipped key is unreachable from source.

## Risks

- No snapshot safety net: hundreds of inline English assertions. Default-English
  behavior is mandatory to avoid a mass rewrite.
- Late-bound strings: module-init literals cannot react to locale changes.
- Width: Russian is longer; status line, approval dialogs, and tables truncate.
- Protocol copy: ACP/RPC option labels are consumed by clients; keep answer ids
  stable and version protocol-visible changes.
- Plugin trust: validate manifests and catalogs, cap size, namespace keys.
- Build: catalogs must be statically imported; keep each under 256 KiB to avoid
  the JSON sidecar path, or split per locale.
- Shell completions: translated descriptions must stay single-line and
  quote-safe.
- Environmental tests: `LANG`/`TZ`/`Intl` oracles must keep deterministic modes.
